# CyberWatch Thailand

ระบบรวบรวมข้อมูลจัดซื้อจัดจ้างด้าน Cybersecurity ที่ตรวจย้อนกลับได้ทุกแถว ไม่ใช่ dashboard mockup

## สถานะข้อมูล

**ไม่มีข้อมูล demo/mock อยู่ในระบบแล้ว** ชุดข้อมูลตัวอย่างจาก prototype (25 รายการ) ถูก **ลบออกถาวร** พร้อม provenance ของมัน และ URL supplier portal ภาคเอกชน 6 แห่งที่ prototype เดาไว้ก็ถูกลบทิ้งเช่นกัน โค้ดที่เคยสร้างข้อมูลตัวอย่าง (`INITIAL_TENDERS`, `ENABLE_DEMO_DATA`, `POST /api/scan/simulate-discovery`) ถูกถอดออกทั้งหมด จึงไม่มีทางกลับมาอีก

ทุกแถวที่เหลือมาจากการดึงสดจากแหล่งจริง และเก็บหลักฐานไว้ต่อรายการ:

- URL หลักฐาน, SHA-256 ของ payload, เวลาที่พบ/ตรวจล่าสุด และประวัติ provenance ทุกครั้งที่พบ
- ระบบไม่สร้าง TOR, source snapshot, งบประมาณ, วันประกาศ หรือวันยื่นซองขึ้นเอง — ฟิลด์ที่ต้นทางไม่ให้จะเป็น `null`
- ถ้าต้นทางไม่ให้วันยื่นซอง ระบบใช้ `UNKNOWN` หรือสถานะที่ต้นทางระบุ เช่น `IN_PROGRESS` ไม่ตีความว่า `OPEN`

สถานะความน่าเชื่อถือ:

| สถานะ | ความหมาย |
|---|---|
| `VERIFIED` | ระเบียนมาจาก structured API/JSON ของหน่วยงานต้นทางและเก็บ payload หลักฐานแล้ว |
| `PENDING` | พบในหน้า HTML/PDF ทางการ แต่ field mapping จาก parser ยังต้องตรวจทาน |
| `REJECTED` | QA พบว่าไม่ใช่ประกาศซื้อจ้างหรือหลักฐานไม่พอ จึงกักออกจากผลปกติ (ยังเก็บไว้เพื่อ audit) |

> `VERIFIED` ยืนยันว่า “ระเบียนและค่าที่แสดงตรงกับแหล่งต้นทาง” ไม่ได้ยืนยันว่าโครงการยังเปิดรับข้อเสนออยู่ ผู้ใช้ต้องตรวจสถานะและกำหนดเวลาจากเอกสารล่าสุดของเจ้าของโครงการก่อนดำเนินการ

## มุมมองเริ่มต้น

หน้าเว็บแสดง **เฉพาะประกาศที่ต้นทางลงวันที่ไว้ และอายุไม่เกิน 1 ปีนับจากวันประกาศ เรียงจากใหม่ไปเก่า**

ระเบียนที่ต้นทางไม่เคยลงวันประกาศ (e-GP ส่งค่า `-` มา) จะไม่ถูกแสดง เพราะพิสูจน์อายุไม่ได้ จึงยืนยันไม่ได้ว่าอยู่ในกรอบ 1 ปี — ไม่ใช่การเดาว่าเก่าหรือใหม่

และ **ไม่แสดงโครงการที่มีผู้ชนะแล้ว** — ถ้าหลักฐานที่เก็บไว้ระบุคู่สัญญาและชื่อผู้ชนะ แปลว่าการแข่งขันจบไปแล้ว ไม่ใช่โอกาสยื่นข้อเสนอ (จากข้อมูลจริง: 120 จาก 191 รายการในกรอบ 1 ปีเข้าข่ายนี้ เหลือโอกาสจริง 71 รายการ) ระเบียนเหล่านั้นยังอยู่ในฐานเพื่อดูว่าใครชนะที่ราคาเท่าไร เรียกดูได้ด้วย `include_awarded=true` หรือ `opportunity_scope=AWARDED`

ปรับกรอบเวลาได้ด้วย `max_age_days` (`0` = ไม่จำกัด) ซึ่งใช้กับทั้งรายการ, CSV export และตัวเลข stats พร้อมกัน ตัวเลขบนการ์ดจึงตรงกับรายการที่เห็นเสมอ

## แหล่งข้อมูล

### 1. e-GP / GovSpending — ครอบคลุมหน่วยงานรัฐทั้งประเทศ

หน่วยงานรัฐไทยทุกแห่ง (กระทรวง กรม รัฐวิสาหกิจ องค์การมหาชน มหาวิทยาลัย โรงพยาบาล อปท.) ต้องประกาศจัดซื้อจัดจ้างผ่าน e-GP แหล่งนี้จึงเป็นตาข่ายที่กว้างที่สุดที่ดึงได้โดยชอบ

- endpoint ค้นแบบ substring คำค้นจึงใช้ "ราก" ที่กว้าง (`ความมั่นคงปลอดภัย`, `ไซเบอร์`, `ภัยคุกคาม`, `ช่องโหว่`, `security`, `SIEM`, `XDR`, …) ซึ่งครอบคลุมทุกวลีย่อยที่สร้างจากรากนั้น กว้างกว่าและใช้คำขอน้อยกว่าการไล่วลีแคบทีละคำ
- ปีงบประมาณที่ค้นมาจาก `get/egp/years` ของต้นทางเอง (บริการเปิดถึงปี 2558) การสแกนปกติย้อน 5 ปี ปรับได้ที่ config
- endpoint คืนผลทั้งชุดในคำขอเดียวเมื่อ `limit` พอ จึงยิงคำขอเท่าที่จำเป็นและหน้าถัดไปเฉพาะเมื่อหน้าก่อนเต็ม
- **เสริมข้อมูลสัญญาและผู้ชนะ** จาก `get/egp/project_detail` ของบริการเดียวกัน ทำให้เห็นว่าโครงการไหนมีผู้ได้รับคัดเลือกแล้ว ราคาเท่าไร (จำกัดจำนวนคำขอต่อรอบ)

การค้นแบบกว้างต้องมาคู่กับตัวกรองที่แม่น เพราะคำค้นเดียวกันมีความหมายอื่นในบริบทอื่น `_is_cyber_record` จึงตัดสินทีละรายการจากชื่อโครงการจริง:

- ตัด "บริบทที่ไม่ใช่ไซเบอร์" ก่อนเสมอ — โควิด/โคโรนา/หน้ากากอนามัย/วัคซีน/ยา/น้ำยาตรวจ, ถนน/ก่อสร้าง/เชื้อเพลิง, รปภ.อาคาร/ดับเพลิง, อาหารกลางวันและโปรเจกเตอร์ที่ซื้อ *ให้* โครงการไซเบอร์
- รับเมื่อพบวลีไซเบอร์ชัดเจน หรือ acronym ที่เป็นคำเต็ม (`SIEM`, `XDR`, `WAF`…) เท่านั้น จึงไม่ถูกหลอกด้วย `ZOLEDRONIC` (มี "edr") หรือ `DLP Projector`
- รับเพิ่มเมื่อพบ "คำใบ้ด้านความปลอดภัย" คู่กับ "คำใบ้ด้านไอที" เช่น "ความมั่นคงปลอดภัย" + "ดิจิทัล/เครือข่าย/สารสนเทศ" ซึ่งครอบคลุมประกาศที่เขียนกว้างโดยไม่ระบุชื่อผลิตภัณฑ์

ตัวอย่างจริงที่ตัวกรองต้องแยกให้ออกถูกใส่ไว้เป็น regression test แล้ว: "ซื้อวัสดุสำหรับศูนย์ฉีดวัคซีนป้องกันไวรัส Covid-19" ต้องไม่เข้า ส่วน "ประกวดราคาซื้อโปรแกรมป้องกันไวรัสคอมพิวเตอร์ (Antivirus)" ต้องเข้า

ถ้ามี `DATA_GO_TH_API_KEY` จะใช้ documented data.go.th API ก่อน แล้ว fallback มา public endpoint

### 2. แหล่งที่ให้ *เอกสารและกำหนดเวลา* ที่ e-GP feed ไม่มี

| แหล่ง | สถานะ | หมายเหตุ |
|---|---|---|
| สกมช. (NCSA) | ใช้งาน | JSON feed ที่เว็บทางการใช้จริง; ถ้า feed ค้างเกิน 365 วันจะรายงาน `PARTIAL / STALE_SOURCE` |
| ธปท. (BOT) | ใช้งาน | อ่าน JSON listing ตัวเดียวกับที่หน้าเว็บทางการเรียก ครบทั้ง 10,862 แถว พร้อมลิงก์เอกสารประกาศ |
| PEA | ใช้งาน | ตาราง `/procurement/list` เดินหน้าถัดไปด้วย query string พร้อม PDF ประกาศ |
| กฟผ. (EGAT) | ใช้งาน | ตาราง `/procure/procure_list.php` พร้อมเลขโครงการ e-GP |
| DGA | ใช้งาน | selector เฉพาะแหล่ง |
| ETDA | ใช้งาน | selector เฉพาะแหล่ง |
| ก.ล.ต. (SEC) | **ปิด** | WAF ตอบ HTTP 403 กับ client ที่ไม่ใช่เบราว์เซอร์ทุกคำขอ |
| ทอท. (AOT) | **ปิด** | หน้ารายการเรนเดอร์ด้วย JavaScript, HTML ที่ส่งมาไม่มีแถวให้ parse |

สองแหล่งที่ปิดยัง **ไม่ได้หายไปจากระบบ** ประกาศของทั้งสองหน่วยงานยังถูกเก็บผ่านช่องทาง e-GP ที่ข้อ 1 การปิดไว้คือการไม่แกล้งรายงานว่า “สแกนสำเร็จ พบ 0 รายการ” ทั้งที่ดึงไม่ได้จริง

#### หมายเหตุเรื่อง ธปท. — ทำไมเคยดึงไม่ได้

listing ของ ธปท. มีสองกับดักที่ทำให้ดูเหมือนไม่มีข้อมูล ทั้งที่มีอยู่ 10,862 แถว:

1. **segment ที่ 3 ของ URL คือ "เลขหน้า" ไม่ใช่ "offset"** ถ้าตีความเป็น offset แล้วคูณด้วยขนาดหน้า จะข้ามแถวทิ้งไป 999 จากทุก 1,000 แถว
2. **หน้าที่ CDN ยังไม่เคยแคช จะ timeout เสมอ** ต่อให้รอ 180 วินาที แต่คำขอนั้นเองคือสิ่งที่ทำให้ต้นทางสร้างและแคชไว้ — ยิงซ้ำอีกครั้งหลังเว้นช่วงจะได้ผลทันทีใน 0.2 วินาที

adapter จึงเดินด้วยเลขหน้า และเมื่อ timeout จะ "เว้นช่วงแล้วยิงซ้ำ" (10 → 20 → 40 วินาที) โดยมีงบเวลารวมต่อรอบสแกน หน้าไหนยังเย็นอยู่จะถูกยกไปรอบถัดไปซึ่งจะเจอแคชอุ่นแล้ว การสแกน 3 รอบแรกจึงไล่จาก `PARTIAL` (45 → 83 รายการ) ไปจนถึง `SUCCESS` ครบทุกหน้า

### หาหน้า procurement ของบริษัทเอง — และผลที่ได้

`backend/discover_procurement_pages.py` ไล่หาหน้าประกาศจัดซื้อบนเว็บบริษัทเอง แทนการเดา URL ทีละอัน: อ่าน `robots.txt` แล้วเคารพ → ลองเส้นทางที่บริษัทไทยใช้จริง → อ่าน sitemap → **พิสูจน์ว่าหน้านั้นเป็นบอร์ดประกาศจริง** (ยังอยู่หลัง redirect, มีคำแบบประกาศจัดซื้อ, และมีแถวซ้ำที่มีวันที่)

```bash
PYTHONPATH=. backend/venv/bin/python backend/discover_procurement_pages.py --json findings.json
```

ผลจากการรันจริง 40 บริษัท:

| ผลลัพธ์ | จำนวน |
|---|---|
| ไม่มีหน้า procurement เลย | 24 (SCG, PTT, CP, True, AIS, ธนาคารทุกเจ้า) |
| มีหน้าพูดถึงจัดซื้อแต่ไม่มีรายการ | ที่เหลือส่วนใหญ่ |
| **บริษัทเอกชนที่มีบอร์ดประกาศจริง** | **0 จาก 24** |

นี่ไม่ใช่ข้อจำกัดของ crawler แต่เป็นโครงสร้างตลาด: **พ.ร.บ.จัดซื้อจัดจ้างฯ 2560 บังคับเฉพาะหน่วยงานรัฐ** เอกชนไทยไม่มีหน้าที่ตามกฎหมายต้องประกาศ RFP จึงใช้ระบบทะเบียนคู่ค้า (AVL) แล้วส่ง RFP ตรงถึงรายที่ลงทะเบียนไว้

ผลที่ตามมาต่อการใช้งาน: ช่องทางเข้าถึงงานเอกชนคือ **ไปลงทะเบียนเป็นคู่ค้ากับแต่ละบริษัท** ไม่ใช่การ scrape ส่วนสิ่งที่ระบบนี้ทำได้จริงคือครอบคลุมหน่วยงานรัฐและรัฐวิสาหกิจ (ซึ่งรวมบริษัทมหาชนของรัฐอย่าง ทอท./ปตท./กฟผ./NT ที่เป็นผู้ซื้อรายใหญ่ด้านไซเบอร์อยู่แล้ว)

### 3. Custom HTML, RSS/Atom และ XML sitemap

เพิ่ม URL และ CSS selector ได้จากหน้าจัดการแหล่งข้อมูล รองรับ `page_url_template` สำหรับเว็บที่เดินหน้าด้วย query string โดยไม่มีลิงก์เลขหน้า ค่าเริ่มต้นต้องพบทั้งบริบท “Cybersecurity” และ “จัดซื้อจัดจ้าง” เพื่อลดข่าว/นโยบายที่ติดมาโดยผิดพลาด

crawler เคารพ `robots.txt`, จำกัดความเร็ว/ขนาด response, ตรวจ redirect และป้องกัน SSRF

## ดึงข้อมูลย้อนหลังให้ครบ (backfill)

การสแกนตามรอบตั้งใจให้เบา (ย้อน 5 ปี ทุก 30 นาที) ส่วนการกวาดประวัติทั้งหมดให้ใช้สคริปต์นี้:

```bash
PYTHONPATH=. backend/venv/bin/python backend/backfill_egp.py
```

ตัวเลือก: `--years-back 12` (ค่าเริ่มต้น ครบทุกปีที่บริการมี), `--no-details` (ข้ามการดึงสัญญา/ผู้ชนะ เร็วกว่ามาก), `--max-detail-requests`, `--concurrency`

สคริปต์ใช้ adapter ตัวเดียวกัน endpoint เดียวกัน และเก็บหลักฐานแบบเดียวกับการสแกนปกติ ต่างแค่ช่วงปีที่กว้างกว่า

## ข้อจำกัดที่ตั้งใจแสดงอย่างตรงไปตรงมา

ไม่มีระบบใดรับประกัน “ทุกข้อมูลบนอินเทอร์เน็ต 100%” ได้ เว็บที่ต้อง login, CAPTCHA, JavaScript-only, paywall, robots.txt ห้าม หรือไม่มี public index จะดึงไม่ได้โดยชอบธรรม ระบบนี้จึงรายงานผลรายแหล่งเป็น `SUCCESS`, `PARTIAL`, `FAILED` หรือ `SKIPPED` และไม่ถือว่า “พบ 0 รายการ” เท่ากับ “สแกนสำเร็จ” เมื่อ request ล้มเหลว

e-GP/GovSpending มีทั้งข้อมูลโครงการและสัญญา จึงใช้เป็น procurement intelligence ได้ แต่ไม่ควรถือทุกแถวเป็น bid ที่ยังเปิดอยู่ โดยเฉพาะรายการที่ไม่มี submission deadline หรือรายการที่มีข้อมูลสัญญาแล้ว (แปลว่ามีผู้ได้รับคัดเลือกไปแล้ว)

## เริ่มใช้งาน (เครื่องตัวเอง)

```bash
./start.sh
```

- API docs: <http://localhost:8000/docs>
- Health check: <http://localhost:8000/api/health>

สมัคร key จาก <https://opend.data.go.th/register_api> แล้ว export ก่อนรัน:


## API ที่เกี่ยวกับความน่าเชื่อถือ

```text

GET  /api/tenders?verified_only=true
GET  /api/tenders?official_only=true

GET  /api/tenders?include_quarantined=true   # audit เท่านั้น
```

## ทดสอบ

```bash
PYTHONPATH=. backend/venv/bin/python -m unittest discover -s backend/tests -v
npm run build --prefix frontend
```

ชุดทดสอบครอบคลุมการลบข้อมูล prototype ทิ้งจริง, API trust filter, การไม่สร้าง TOR, structured scan outcome, stable evidence hash, การเสริมข้อมูลสัญญาโดยไม่แต่งฟิลด์ที่หายขึ้นมา, การอ่านรายการปีจากต้นทาง, ฟิลด์ที่หายต้องคงเป็น `null`, การรวม provenance จากหลายแหล่งโดยไม่ทับแหล่งหลัก และตัวกรองความเกี่ยวข้องที่ทดสอบด้วยชื่อโครงการจริงทั้งฝั่งที่ต้องรับและฝั่งที่ต้องตัด

## ฐานข้อมูลและการกู้คืน

ฐานหลักคือ `cyber_opp.db` การอัปเกรดจะเพิ่ม trust columns แบบ idempotent แล้วลบข้อมูล prototype ทิ้ง สำรองไว้ที่:

- `cyber_opp.pre-demo-purge-*.db` — ก่อนลบข้อมูล demo 25 รายการและแหล่งสมมติ 6 แห่ง
- `cyber_opp.pre-relevance-purge-*.db` — ก่อนตัดรายการที่ตัวกรองรุ่นแก้ไขแล้วไม่รับ (ส่วนใหญ่เป็นพัสดุโควิดที่ติดมาจากคำว่า "ป้องกันไวรัส")
- `cyber_opp.pre-bot-fix-*.db` — ก่อนเพิ่มระเบียนจาก ธปท.

อย่านำผลจากระบบไปยื่นเสนอราคาโดยไม่เปิดประกาศ/เอกสารล่าสุดจาก URL ต้นทางอีกครั้ง
